# إعادة تقييم شاملة للنظام

التاريخ: 2026-07-03
النظام: QIB Service Portal
النطاق: الواجهة React، خلفية FastAPI الحالية، خلفية ASP.NET Core المستقلة، قواعد البيانات، الإعدادات، الوثائق، المراسلات، الطلبات، التقارير، الصحة، النشر.

## الخلاصة التنفيذية

النظام أصبح واسعاً ومتكاملاً على مستوى الوظائف، خصوصاً بعد إضافة نسخة ASP.NET Core المستقلة وربطها بقاعدة PostgreSQL منفصلة. الواجهة تبنى بنجاح، وخلفية .NET تعمل صحياً على Docker، كما أن Swagger متاح ويعرض عدداً كبيراً من المسارات.

لكن النظام لا يزال غير جاهز للإنتاج النهائي دون إغلاق عدة نقاط عالية الأهمية: اختبارات آلية قابلة للتشغيل، ترحيلات EF Core رسمية بدلاً من الاعتماد على إنشاء/تصحيح الجداول وقت التشغيل، إصلاح WebSocket/الإشعارات، تنظيف ملفات `bin/obj` المتتبعة في Git، وتثبيت سياسة أسرار وإعدادات إنتاجية.

تقدير الجاهزية الحالي:
- مناسب للتجربة الداخلية: نعم.
- مناسب لبيئة staging مضبوطة: نعم، بشرط تنفيذ قائمة ما قبل التشغيل.
- مناسب للإنتاج مباشرة: لا، يحتاج إغلاق النقاط الحرجة أدناه.

## ما تم فحصه

تم تنفيذ فحوصات فعلية على المشروع المحلي:

- بناء الواجهة: `npm run build`
- تجميع Python: `python3 -m compileall backend/app`
- بناء صورة Docker لخلفية .NET: `docker compose build qib-dotnet-api`
- صحة خدمة .NET: `GET http://localhost:8088/api/dotnet/v1/health/live`
- Swagger/OpenAPI لخلفية .NET
- عدد جداول PostgreSQL المستقلة للـ .NET
- حالة Docker Compose للـ .NET
- البحث عن TODO/NotImplemented/mock
- فحص الملفات المتتبعة غير المناسبة مثل `bin/obj`
- مراجعة إعدادات Swagger و JWT و CORS و التشغيل

## نتائج الفحص

### الواجهة React

الحالة: ناجحة

نتيجة البناء:
- تم بناء الواجهة بنجاح.
- Vite أنهى البناء بدون فشل.
- أكبر ملف واضح هو ملف التطبيق الرئيسي وملف المراسلات، وهذا طبيعي مع حجم النظام، لكنه يحتاج مراقبة مستمرة.

ملاحظات:
- الواجهة تدعم ربط FastAPI أو .NET عبر `VITE_API_BASE_URL`.
- يوجد ملف `frontend/.env.dotnet` مناسب لتشغيل الواجهة على API الجديد.
- لا تزال بعض الشاشات تحتاج اختبارات سيناريو فعلية لضمان تطابق السلوك مع FastAPI.

### خلفية ASP.NET Core

الحالة: تعمل، لكنها تحتاج تقوية إنتاجية.

نتائج مهمة:
- Docker build نجح.
- الخدمة تعمل على `http://localhost:8088`.
- Health endpoint يرجع `Healthy`.
- Swagger المباشر يعمل.
- OpenAPI يحتوي تقريباً على:
  - 294 مساراً
  - 360 عملية
- قاعدة PostgreSQL المستقلة تحتوي على 79 جدولاً.

نقاط قوة:
- فصل واضح عن FastAPI عبر `/api/dotnet/v1`.
- JWT وجلسات وربط صلاحيات موجودة.
- جداول تشغيل مهمة موجودة مثل الجلسات، محاولات الدخول، الصحة، النسخ، التحديثات، التقارير، AI، والمراسلات.
- العمليات الخطرة محمية بإعداد `EnableDangerousDatabaseOperations`.

نقاط خطر:
- لا توجد EF Core migrations واضحة في المشروع حالياً.
- `Program.cs` يستخدم `EnsureCreatedAsync` عند عدم تفعيل `ApplyMigrationsOnStartup`، ثم يشغل `RuntimeSchema.EnsureAsync`.
- هذا مناسب للتطوير، لكنه غير مثالي للإنتاج؛ الإنتاج يحتاج ترحيلات رسمية قابلة للمراجعة والتراجع.
- Swagger مفعل افتراضياً في إعدادات التطوير، ويجب تعطيله أو حصره داخلياً في الإنتاج.
- `Jwt__Secret` وبيانات المدير الافتراضية في ملفات التطوير يجب تغييرها قبل الإنتاج.

### خلفية FastAPI

الحالة: موجودة وتُجمع بنجاح، لكن الاختبارات لم تعمل في البيئة الحالية.

نتائج:
- `python3 -m compileall backend/app` نجح.
- الاختبارات لم تنفذ لأن بيئات Python الحالية لا تحتوي `pytest`.

ملاحظة:
غياب `pytest` ليس فشلاً وظيفياً في النظام، لكنه يمنع إصدار حكم اختبار كامل. يجب تجهيز بيئة اختبار ثابتة أو Docker test runner.

### الإشعارات و WebSocket

الحالة: تحتاج إصلاح قبل الإنتاج.

سجلات Docker أظهرت أخطاء WebSocket:
- `The remote party closed the WebSocket connection without completing the close handshake`
- ثم محاولة middleware كتابة headers بعد بدء الاستجابة:
  - `Headers are read-only, response has already started`

الأثر:
- قد تظهر أخطاء 500 عند قطع اتصال WebSocket.
- قد تتأثر تجربة الإشعارات الحية.

التوصية:
- التعامل مع `WebSocketException` داخل `RealtimeController` كإغلاق طبيعي.
- عدم تمرير استثناء WebSocket إلى `ExceptionHandlingMiddleware` بعد بدء الاستجابة.
- إضافة اختبار اتصال/قطع WebSocket.

### الصلاحيات والأمان

الحالة: جيدة في الهيكل، تحتاج تبسيط واختبارات.

الموجود:
- سياسات `Permission:*` مستخدمة على معظم Controllers.
- بعض المسارات العامة مقصودة مثل login و public profile و health live و swagger.
- العمليات الخطرة محمية.
- جلسات المستخدم موجودة وتدعم الإنهاء.

نقاط تحتاج مراجعة:
- تبسيط نموذج الصلاحيات للمستخدم النهائي إلى عرض/تعديل، مع إبقاء الصلاحيات الدقيقة داخلياً.
- اختبار نطاق البيانات لكل دور:
  - موظف
  - مدير مباشر
  - مدير إدارة
  - مختص قسم
  - مدير نظام
- التأكد أن مدير إدارة لا يرى إلا نطاقه الصحيح.
- التأكد من عدم ظهور أزرار لا يستطيع المستخدم تنفيذها.

### المراسلات

الحالة: واسعة الوظائف، لكنها تحتاج اختبار انعكاس الإعدادات.

النظام يحتوي على:
- أنواع رسائل
- تصنيفات سرية
- قوالب
- إعدادات مرفقات
- إعدادات AI
- ربط بالطلبات
- مراسلات رسمية
- تواقيع
- إشعارات

نقاط يجب تثبيتها:
- عند تعطيل نوع رسالة لا يظهر في الإنشاء.
- عند تعطيل تصنيف سرية لا يظهر في الإنشاء.
- عند تعطيل إشعارات المراسلات لا تُنشأ إشعارات.
- طلب الاستيضاح يحترم إعداد `requires_request`.
- قراءة الرسالة تحدث عند فتحها من المستلم.
- الرد لا يغير نوع الرسالة إلى رسمية إلا إذا كان مسموحاً ومكتمل الشروط.
- PDF الرسمي يعرض النص كنص عادي لا HTML خام.

### الطلبات والموافقات

الحالة: الوظيفة موجودة، لكنها تحتاج اختبارات سير عمل كاملة.

نقاط قوة:
- طلبات ديناميكية.
- حقول وسير موافقات snapshots.
- SLA ومرفقات.
- PDF للطلب.
- سجل موافقات وتدقيق.

نقاط تحتاج تحقق:
- الطلب الجديد يأخذ مسار الموافقات الكامل من إعدادات إدارة الطلبات، لا مرحلة واحدة فقط.
- عرض مسار الموافقات يجب أن يستخدم أسماء مفهومة مثل اسم الإدارة/القسم، لا أسماء تقنية فقط.
- أصحاب الخطوة الحالية فقط تظهر لهم أزرار اعتماد/رفض/إرجاع.
- المستخدم الموجود في خطوة اعتماد يجب أن يستطيع فتح تفاصيل الطلب من المراسلات دون 403.
- منفذو الأقسام المختصة يجب أن تُقرأ علاقتهم بالقسم بدقة.
- تعدد المرفقات يجب أن يحترم إعداد `allow_multiple_attachments`.

### الوثائق

الحالة: وحدة الوثائق موجودة وتحتاج ضبط صلاحيات وتجربة.

الموجود:
- تصنيفات وثائق.
- رفع PDF.
- إصدارات.
- إقرارات.
- صلاحيات وثائق.
- سجلات وصول.

نقاط إنتاجية:
- إيقاف التحميل والطباعة يجب أن يطبق Backend وFrontend.
- كل وثيقة يجب أن تعرض من خلال endpoint محمي فقط.
- يجب توضيح شاشة صلاحيات الوثائق للمستخدم الإداري.

### التقارير والإحصائيات

الحالة: تحتاج إعادة تبسيط وربط أعمق.

الملاحظات:
- التقارير كانت نقطة ضعف مذكورة سابقاً بأنها غير مرتبطة بالكامل.
- لوحة الإحصائيات أصبحت تحتوي widgets، لكنها تحتاج توحيد تصميم البطاقات والوضعين النهاري/الليلي.

التوصية:
- جعل التقارير Phase مستقلة بعد تثبيت الطلبات والمراسلات.
- البداية تكون بتقارير تشغيلية قليلة لكنها صحيحة:
  - الطلبات حسب الحالة
  - الطلبات حسب النوع
  - الموافقات المتأخرة
  - الرسائل الرسمية
  - سجل التدقيق
- إضافة حفظ التقارير وجدولتها لاحقاً.

## أهم المخاطر قبل الإنتاج

1. غياب EF Core migrations رسمية.
2. أخطاء WebSocket عند قطع الاتصال.
3. اختبارات FastAPI غير قابلة للتشغيل في البيئة الحالية بسبب غياب `pytest`.
4. لا يوجد مشروع اختبارات .NET واضح.
5. وجود أسرار وكلمات مرور افتراضية في ملفات التطوير.
6. ملفات `bin/obj` متتبعة في Git.
7. بعض الإعدادات المتقدمة قد تكون موجودة كجداول لكنها تحتاج اختبارات تثبت انعكاسها.
8. التقارير لم تصل بعد إلى مستوى الاعتماد الإداري الكامل.
9. تشغيل Swagger يجب ضبطه للإنتاج.
10. تعدد الخلفيات FastAPI/.NET يحتاج استراتيجية cutover واضحة حتى لا يتشتت التشغيل.

## توصية الجاهزية

قبل الإنتاج يجب تنفيذ الآتي بالترتيب:

1. إنشاء EF Core migrations كاملة للـ .NET.
2. تعطيل `EnsureCreatedAsync`/تقليل الاعتماد على `RuntimeSchema` في الإنتاج.
3. إصلاح WebSocket وإغلاق الاتصال الهادئ.
4. إنشاء test runner موحد:
   - Backend FastAPI tests
   - .NET integration tests
   - Frontend build
   - Scenario tests
5. تنظيف `bin/obj` من Git.
6. تغيير كل الأسرار الافتراضية.
7. إغلاق Swagger أو حصره داخلياً.
8. تنفيذ اختبار سيناريو كامل:
   - إنشاء طلب
   - مسار موافقات متعدد
   - مرفقات متعددة
   - مراسلة مرتبطة
   - إشعار
   - PDF
   - تقرير
9. مراجعة صلاحيات كل دور على بيانات حقيقية.
10. تجهيز خطة نشر و rollback.

## الحكم النهائي

النظام وصل إلى مرحلة متقدمة جداً من التطوير، لكنه حالياً في مستوى pre-production وليس production-ready. أقوى مسار الآن هو تثبيت نسخة .NET كمنصة مستقبلية، مع إبقاء FastAPI مرجعاً وظيفياً إلى أن تجتاز .NET اختبارات السيناريوهات كاملة.

الأولوية القادمة المقترحة:
1. إصلاح WebSocket والإشعارات.
2. إنشاء EF migrations.
3. تنظيف Git من مخرجات البناء.
4. بناء اختبارات سيناريو آلية للطلبات والموافقات والمراسلات.
5. إعادة تقييم التقارير بعد تثبيت مصادر البيانات.
